# Claims register

Every user-facing security claim, graded **TRUE**, **TRUE-WITH-CAVEATS**
(caveats named), or **NOT-MADE**. A claim may not appear in README,
PRIVACY, UI copy, or marketing unless it appears here with a grade and an
enforcing reference. If code and this register disagree, one of them is a
bug — same rule as PROTOCOL.md.

Permanently NOT-MADE, never to appear anywhere: "uncrackable",
"military-grade", "no metadata", "messages never leave your devices".

| Forward secrecy (wire-capture, scoped) | TRUE-WITH-CAVEATS — the §1.4 generation ratchet is live: rooms rotate to fresh random generation secrets on joins and leaves, and every 15 minutes or 200 messages while active, so relay-archived ciphertext of generations ≥1 stays unreadable to a passive operator even given a later-leaked link, and retired generations' keys are destroyed two ratchets on. Since v4, generation secrets transit only **hybrid-wrapped per recipient device** (X-Wing: X25519 + ML-KEM-768), so a grant captured at an endpoint or recovered from recorded DTLS by a future quantum attacker stays unreadable without that device's key store. Named exclusions, which must ride any user-facing statement: a leaked link still grants *entry* + history-by-sync (capability model, visible as a joining peer); at-rest history stays under static `k_storage` (§4); compromise of a recipient device's key store opens grants addressed to it (and its at-rest history regardless); an active link-holder at grant time is simply a member; relay-only peers cannot receive rotations (stranded, shown in UI); a member's own ratchet griefing is availability-only (§1.4/§6); the PQC implementation (`@noble/post-quantum`, pure JS, exact-pinned) is FIPS-203/204-final and Wycheproof/ACVP-tested but **not independently audited** — no independently audited pure-JS PQC exists (2026-06). Never stated unqualified | PROTOCOL.md §1.3/§1.4 v4; `src/lib/crypto/kem.ts` (X-Wing wrap, AAD-bound), `src/lib/p2p/ratchet.ts` + `crypto-session.ts` (engine, trial decrypt, per-recipient wrapped grants, direct-only); `tests/unit/kem.test.ts`, `ratchet-engine.test.ts`, `session.test.ts` (§7 v4 rows); `required-ratchet.spec.ts` (join→rotation E2E, relay stranding); scoped wording in README "Honest limits" |
| Post-quantum content confidentiality | TRUE-WITH-CAVEATS — content keys are symmetric-only (Grover leaves ~128-bit effective strength), and since v4 the one asymmetric path near content — generation-secret distribution — is hybrid post-quantum (X-Wing), closing harvest-now-decrypt-later on grants. ECDSA signatures remain quantum-forgeable — an authenticity risk against link holders only, not confidentiality (Phase-2 item 9: documented posture with rotation trigger); the DTLS transport layer is classical ECDHE in most engines (Chrome 142+ is hybrid-PQ) but only wraps already-E2E ciphertext and is browser-controlled | Key schedule PROTOCOL.md §1, §1.4 Quantum note (v4), threat model §6 |
| No accounts, analytics, tracking, third-party scripts, or runtime CDN | TRUE | CSP in `svelte.config.js` (self + hashed inlines); `connect-src` pinned to self + the build-time signaling origin (no scheme-wide `ws:`); self-hosted fonts; no third-party script or fetch origins (ICE uses Cloudflare STUN/TURN, the CDN already in the path; PRIVACY.md) |
| You don't have to trust the server with content | TRUE-WITH-CAVEATS — you re-trust the *served JavaScript* on every page load; a malicious build could exfiltrate keys. This is the ceiling of every web-delivered messenger vs an installed, signed app. SRI does not raise it (the adversary serves the entry HTML); builds are now reproducible and anyone can compare the served bundle with a build of its commit (`scripts/bundle-digest.mjs`, daily `verify-live.yml`), which catches a swapped build but not one served only to a target; a pinned verifier remains the genuine fix | E2E encryption design; ceiling disclosed in README "Honest limits"; full analysis in `docs/BUNDLE_VERIFICATION.md` |
